### D48: The live smoke of the MCP server, what it found, and the README
- Date: 2026-11-05
- Decision: `scripts/smoke_mcp.py` (with `smoke_mcp_flows.py`, `smoke_mcp_run.py` and the pure `smoke_mcp_checks.py`, split to stay under the line cap) is a manual live smoke of the real server, gated exactly like `smoke_edgar.py` and the recorder: it refuses unless `LISTINGLENS_ALLOW_NETWORK=1`, sits outside `testpaths`, and CI never runs it. It starts the server as a child process (`python -m listinglens.server`) and drives it over stdio with the SDK's client, with a read timeout of 120 seconds, so the environment, the entry point, the lifespan and the child's stderr are all the real ones. It checks plausibility and never exact values: the company, the tickers, a date of today, newest-first filings that add up, a form filter that is exact, every figure a decimal string with a dashed accession, the tier-table row a result sits in, a directory stamp and hash of the right shape, every finding's measured value equal to the same concept in `extract_financials`. Each call's wire size is judged against the D47 ceilings, and an overrun is a finding, not a failure, because those ceilings came from four recorded companies. The script makes 58 measured tool calls (plus 4 error probes) to 12 companies, 13.2 seconds of call time in all, and fixes nothing.
- The SEC contact: the script reads it with `Settings()` (the environment or `.env`; the server itself still never reads `.env`) and gives it to the child only through its environment block, with an absolute temporary cache directory and the log level, so it is on no command line. It is never printed, logged or written: every line goes through a redaction, the raw text of every line is counted for the contact before it is redacted, the child's stderr goes to a file the script owns and is scanned, and the run fails if the contact appears anywhere. The cache is a fresh temporary directory removed at exit, so every run is cold and nothing is left in the repository. Result of the live run: the contact appeared 0 times in the script's output and in the server's 38 stderr lines.
- Live run, 2026-11-05 (the Nasdaq directory file was 0 days old, stamp `1105202608:31`, 5,610 rows; the server started in 3.05 seconds). It ran twice: the first run found three defects in the script itself, not in the server, which were fixed and the run repeated. The SDK's `send_ping` is removed as of 2026-07-28 and only works in legacy mode, so the stall probe now sends a `tools/list` request that skips the client's cache; the staleness detector had flagged `public_float` (measured at the end of the second quarter, and dated apart from the fiscal figures, like the cover-page share count) for the 2025 and 2026 filers, so those two concepts are excluded from it; and Trans American's expected ticker and tier row became findings because the SEC no longer lists a ticker for it. The second run: 142 checks passed, 0 failed, 17 findings. Slowest call 1.63 seconds (GE `extract_financials`, cold), most calls 0.05 to 0.6 seconds, no read timeout fired. The largest wire sizes against their ceilings: `resolve_company` 2,360 bytes for BMO (ceiling 1,100); `list_filings` at the cap of 100 58,578 (64,000); `extract_financials` 15,722 for ATA Creativity (15,000); `check_standards` for one tier or none 49,700 for Credit Suisse AG (52,000), and for an initial listing with three tiers 154,142 for Xiao-I (180,000). Only those three call kinds exceed a ceiling, and only because a live issuer is bigger than the four recorded ones.
- Large filer: Citigroup's companyfacts is 9,019,678 bytes decoded (8.60 MiB, 593 KB compressed) and was the largest of 24 documents measured; fetched directly it took 0.44 seconds and through the server `extract_financials` took 0.62 seconds (9 figures, no gaps). The response cap is 50 MiB of decoded bytes, so the largest real document is 5.8 times below it. No live filer approaches the cap, so the smoke can report the headroom but cannot exercise the refusal; the transport test with a patched cap remains the only proof of it.
- The event loop: while a call runs, the server answers nothing else (D42, D47). A `tools/list` request sent 50 milliseconds into a call was answered only after the call ended: 0.57 seconds into Citigroup's 0.62 second `extract_financials`, 0.07 seconds into Xiao-I's initial three-tier check (0.13 seconds) and 0.29 seconds into a repeated GE check (0.35 seconds). So the wait a host would see is the length of the call it is waiting on, at most 1.63 seconds in this run, with no timeout. What this does not show is a host: the smoke's client is the SDK's, with a 120 second timeout. Whether Claude Desktop or Claude Code cancels, times out or delays a second request is the open question for the manual step after this commit, together with which payload (the text copy, the structured content, or both) the host gives the model.
- Findings, none fixed here. F-live-1 (reproduced): ATA Creativity's `income_from_continuing_operations` is -5,280,357 for the period ending 2021-12-31 (20-F accession 0001564590-22-015529) while the other seven figures end 2025-12-31 (accession 0001104659-26-037267); a defect, and Phase 3 does not close until it is fixed. F-live-2 (reproduced): all seven of AGM Group's figures cite form `POS AM` with no fiscal period, and its share count and public float are gaps; D31's deferred prefer-annual tie-break, triaged after F-live-1. L3 (new, blocking, same status as F-live-1): when a company's only Nasdaq listings are exchange-traded notes or funds, the operating-company continued-listing standards do not apply to that issuer, and assessing it against them answers a question that does not exist for it; a cited directory match does not make that defensible. Evidence: Credit Suisse AG (CIK 1053092) has three tickers, `GLDI` with security name `ETRACS Gold Shares Covered Call ETNs due February 2, 2033`, `SLVO` with `ETRACS Silver Shares Covered Call ETNs due April 21, 2033`, and `USOI` with `ETRACS Crude Oil Shares Covered Call ETNs due April 24, 2037`, each in market category `G`, financial status `N`, ETF flag `Y`, not a test issue; `check_standards` for a continued listing with no tier named returned row 6, tier Global, verdict `cannot_determine`, and its `extract_financials` returned one figure and eight gaps. It belongs to tier selection and gets its own plan pass after the F-live-1 fix; the smoke now prints the security name and the ETF flag of every matched directory row for every company so that pass has the evidence. L4: the D47 ceilings are recorded-fixture ceilings (above); and `resolve_company` carries `tickers` and `exchanges` as two parallel lists full of repeats (BMO: 45 tickers, 45 exchange strings, 2 distinct), so a candidate improvement after Phase 3 is to publish ticker and exchange pairs; nothing changes now. L1: companies that report under IFRS or file 40-F (Royal Bank of Canada and BMO on 40-F, Credit Suisse AG on a 20-F) have companyfacts but the tools read one figure (the cover-page share count) and eight gaps; reading them is Phase 7 work. New: Trans American no longer has a ticker in the SEC's submissions (`tickers []`), so it now lands in tier-table row 4 and not row 5, which D42 recorded for the recorded fixtures; the fixtures are unaffected. L5: the ticker map has no ambiguous ticker and one ambiguous name, `Wiseqey Corp.`, which the smoke asks for and receives as a readable error listing both CIKs (`0001738699` and `0002107968`).
- Confirmed assumptions: D30's missing-companyfacts case is a 404 (its body is an XML `NoSuchKey` document, which nothing reads), and through the live server SPY (CIK 884394) returns `facts_status` `no_xbrl_facts` with no figures or gaps, while `check_standards` for a named tier ran the engine on the empty bag with no findings and no invented gap reason; Silvergate Capital (CIK 1312109, delisted, no tickers) lands in row 4 with facts available; a continued listing with a tier named is row 3, an initial listing with a tier named is row 2 and an initial listing with none is row 1 (three tiers in order). Not reachable live: the response cap, row 7 (no multi-tier issuer was found among those probed) and rows 9 and 10 (the directory cannot be made to fail on demand); they stay covered by tests.
- README: it describes the finished product, not a status snapshot, so it does not need updating each time a phase lands. The original opening and "What it does" list stay as the description of what ListingLens is built to do; what exists today is recorded in DECISIONS.md and in the tools' own published descriptions, which state the current limits to every model that calls them. The Data line now names Nasdaq's symbol directory beside SEC EDGAR, and the old "Run it yourself" placeholder is replaced by a run-it section: uv 0.13.4 or later, no API key, the three environment variables, a host configuration with an env block (Windows with the installed script, macOS or Linux with the module form), exit status 2 for a bad variable, no host product's configuration path named, a note on .env.example, and the manual smoke command.
- Evidence: 32 offline tests of the script (the gate, the redaction and its raw-text leak count, the child's environment, the ceilings and the wire size against the test suite's, the tier-table row classifier, each plausibility rule against a recorded result and a damaged copy, the two finding detectors, the directory-row check for a fund or a note); 25 scripted mutations (the gate, the redaction, the leak count, the environment, a ceiling, the wire size, the staleness threshold and the float exclusion, the source-form rule, the row classifier, the stamp age, the ETF flag, and each rule) were each caught, with the files restored byte for byte.
- Options considered: exact expected values (rejected: the data moves, as Trans American's ticker did); running the server in process (rejected: it would not test stdio, the environment or the child's stderr); a repository-local cache directory (rejected: warm repeat runs and stray `-wal` files in `git status`); failing the run on a ceiling overrun (rejected: the ceilings were set from four companies); recording the live responses as fixtures (rejected: the point of the smoke is that it is live); reading `.env` in the server (rejected again).
- Why: the unit tests prove the server against recorded data, and only a live run shows what real issuers do to it; reporting each surprise with its evidence, and fixing none in the same commit, keeps each later fix reviewable on its own.
- Revisit if: a real host stalls or times out on a call, the live data moves a tier-table row for a company the smoke treats as stable, F-live-1's fix changes the figures a latest-year rule measures, or L3's plan pass changes what a directory match means. Housekeeping: `scripts/record_fixtures.py` (300 lines) and `core/errors.py` (295) are untouched.

### D47: The MCP stdio adapter: a thin server over the in-process service, and what the SDK does and does not do
- Date: 2026-11-01
- Decision: `server/` is the only package that imports the SDK (under both of its import names, `mcp` and `mcp_types`) and holds the stdio adapter over D46's `ToolService`: four `async def` tools named `resolve_company`, `list_filings`, `extract_financials` and `check_standards`, published with the server instructions and tool descriptions approved in D42 (word for word, plain ASCII apostrophes, compared in tests with an independent copy), and annotated read-only, idempotent and open-world. `build_server(open_service)` is the only way to build it: the lifespan enters the context manager `open_service()` on the event-loop thread, keeps the service in a small holder the tools read (the SDK's `Context` parameter is typed with an explicit `Any`, which this repo bans), and leaves it on shutdown. Production passes `open_tool_service` over the settings; tests pass the recorded stack or a stub. It is an argument and nothing else, and an AST guard pins that nothing under `server/` reads `os.environ`, `os.getenv` or a dotenv file (pydantic-settings reading the environment inside `ToolSettings` is the one sanctioned reader), so no process environment can choose what is served. `python -m listinglens.server` and the console script `listinglens-server` both run `startup.main`.
- Parameters: each tool's parameters are the argument models' own annotated aliases (`CikArg`, `FormsArg` and the rest, defined once in `tools/args.py` with their descriptions in `tools/arg_text.py`), as keyword-only parameters, and the first line of each tool builds the C3c model. So the SDK validates exactly what the models validate and publishes the models' constraints and descriptions, and a parity test fails the moment a published input schema differs from its model's. A model-typed parameter would have been nested under its parameter name (`{"args": {...}}`, with the model as a `$ref`), which the SDK does for any Pydantic parameter; the flat form is the natural schema for a model to fill and keeps the three selector tools free of `$ref`. SDK limitation, recorded: the SDK's argument model does not forbid extra keys and offers no way to, so a stray top-level key (`as_of`, `price`, a misspelled field) is dropped before our code runs, and nesting under `args` would not close that gap because a stray key beside `args` would be dropped too. The models still refuse extras, and a test pins that a stray key is ignored while the result's own echoes (`evaluated_on`, `requested_tier`, `tier_source`, and the still-missing market inputs in the caveat) show what was actually used; a wrong key such as `company` reaches the readable request for exactly one of cik, ticker or name. Revisit if the SDK gains a way to forbid extra keys. The argument descriptions were rewritten to say what actually happens (for `tier`: all three tiers for an initial listing, the tier Nasdaq's directory gives for the ticker for a continued one, nothing assessed without a ticker or a match, a failure with the reason if the directory cannot be read, and a named tier always assessed).
- Results: each tool returns `Annotated[CallToolResult, Result]`, a result built by hand with the same data twice: the structured content, and compact JSON as the text copy that the spec expects beside a published output schema. The SDK's own text copy is `indent=2` JSON, which on the recorded companies was 2.3 to 2.8 times the structured size on the wire against 2.1 for compact text. The structured content is the Python-mode dump on purpose: with a `CallToolResult` the SDK validates `structured_content` against the output model in Python mode, and these models are strict, so a JSON-mode dict (ISO date strings, arrays) is refused as an internal failure; the Python-mode dict validates, and the SDK serializes it to the JSON the client receives. The output schema is the model's own schema (not wrapped in `result`), generated by the SDK's strict generator, which raises on any warning and does not for any of the four models; every description lands in it. A test pins that the text parses to JSON equal to the structured content, that the structured content validates as JSON against the model, and that an error is always raised as a `ToolError` and never returned as a result.
- Wire size (content text plus structured content plus `isError`, compact JSON-RPC encoding, the largest over Trans American, Luckin, GE and Xiao-I, with the pinned ceiling): `resolve_company` 970 (1,100), `list_filings` at the default of 20 12,884 (14,000) and at the cap of 100 59,718 (64,000), `extract_financials` 13,666 (15,000), `check_standards` for one continued tier 47,818 (52,000) and for an initial listing with all three tiers 162,912 (180,000). The SDK's indented text would have been 1,071, 14,479, 67,313, 17,426, 63,657 and 214,599, each over its ceiling. Hosts put the text block in front of the model and use the structured content for validation or display, so the text copy is the model-facing cost (about 77 KB compact for the three-tier answer); a host that forwards both pays the wire figure. The ceilings are regression guards, not budgets, and trimming the views still waits for Phase 4 to measure token cost (D46).
- Errors: a context manager inside each tool turns the readable failures into `ToolError`, whose message the SDK sends as `Error executing tool <name>: <message>` with `isError` true and no structured content: `ToolArgumentError`, `AmbiguousCompany` (up to ten `cik (name)` candidates, then a count of the rest, labelled as data, and a request to retry with a cik), `CompanyNotFound`, and `RateLimited`, `UpstreamError`, `MalformedPayload`, `ResponseTooLarge`, `TooManyRedirects` and `UndecodableDocument`. Every message is built from the error's structured fields, never from `str(exc)`, because a free-form detail can carry text taken from an SEC response; that detail is cut to 200 characters and quoted as data, and the full text goes to the log. Everything else is left to the SDK, which tells the caller only `Error executing tool <name>` and logs the traceback at ERROR: the bare `InputValidationError` an engine model raises on a broken invariant (a forged rule set proves it arrives masked, with the bare class found under the SDK's wrapper in the log), `UnrepresentableNumber`, `StandardsError`, `MarginError`, `AllowlistViolation`, `MissingUserAgent` mid-run, and anything else. Arguments the SDK refuses before our code runs (a limit of 101, an unknown enum value, an integer CIK) are readable tool errors with the validation text. The SEC contact is not in any error field; a canary contact is searched for in every result, structured content and log line across successes and failures.
- Process model: unchanged from D42 and now proven end to end. The tools are `async def` and call the synchronous service on the loop thread, the lifespan opens and closes it on that same thread (the SDK awaits an `async def` tool directly, sends a plain `def` tool to `anyio.to_thread.run_sync`, and enters the lifespan inside the loop that `anyio.run` starts in the calling thread). A test fires eight concurrent calls across all four tools through the in-process client and records one thread id equal to the lifespan's, with at most one call in flight (each call holds open briefly so overlap would show); a tool made a plain `def`, or a call dispatched through `to_thread`, fails it. The cost is as in D42: a call blocks the loop, including throttle and retry sleeps, so a cancel or ping waits. Revisit on a remote transport, a second concurrent client, or a host stall seen in the live smoke. The dispatch module behind the SDK's request loop was not read; the test, not an assumption, carries the claim.
- Startup and logging: `ServerSettings` adds an optional `LISTINGLENS_LOG_LEVEL` (default WARNING, case and spaces tolerated) to `ToolSettings` and never reads a `.env` file. Any configuration problem (a missing or placeholder contact, a missing, relative or unusable cache directory, a bad level) prints one stderr message that names the problem by variable and never by value, names both required variables and the host's `env` block, says a `.env` file is not used, and exits 2 with nothing on stdout; the cache directory is created and proved writable before the loop starts. `MissingUserAgent`'s own text tells the reader to copy `.env.example`, which is false for the server, so it is never shown. An unexpected crash after startup exits 1 with the traceback on stderr. Logging: stdout is the protocol wire, so nothing under `server/` prints and the root logger gets one stderr handler before the SDK builds the server; `MCPServer` always calls `logging.basicConfig` on the root logger (default level INFO), which does nothing when the root already has a handler, so ours owns the format and level and the SDK's call is a no-op. `rich` is an optional extra of the SDK and is not installed, so the SDK's own handler would have been a plain stderr handler anyway. The SDK's stdio transport also points file descriptor 1 at stderr while serving, a backstop and not a substitute. Two real subprocess tests: a stdio session whose `tools/list` returns exactly the four tools with their output schemas, descriptions and annotations (the child's environment sets the contact, an absolute cache directory and an unroutable proxy, so any accidental fetch fails fast), and the missing-contact, relative-directory, absent-directory and file-as-directory cases, each exiting 2 with empty stdout even with a `.env` file in the working directory that would have rescued them; the console script is run the same way.
- Dependency: `mcp==2.3.0` is pinned exactly and the lock gains 22 packages, nothing existing moved (httpx 0.28.1, pydantic 2.13.5, pydantic-settings 2.15.0, pyyaml 6.0.3, certifi 2026.10.19 are unchanged) and `uv audit` reports no known vulnerabilities in 50 packages. They are the SDK itself and `mcp-types`, its HTTP stack (`httpx2`, `httpcore2`, and `httpx2-jsfetch`, installed only on emscripten), its HTTP and OAuth server pieces that this stdio server never starts (starlette, uvicorn, sse-starlette, python-multipart, pyjwt with cryptography and cffi and pycparser), and jsonschema with referencing, rpds-py and attrs, opentelemetry-api, click, truststore, and pywin32 on Windows only. Every package has a wheel for Linux and Windows, so CI on Ubuntu compiles nothing and needs no change. The lock file's own revision field moved from 3 to 5 because the pinned `uv` 0.13.4 wrote it. Nothing in `src` imports `httpx2` or `httpcore2`, and the guard from D45 still enforces it.
- Test infrastructure: the autouse socket guard denied the loopback connection that asyncio's event loop makes on Windows (`socket.socketpair` has no native form there), so every async test failed at loop creation. It now lets a connection through only to a loopback IP literal (`127.0.0.1`, `::1`) and still denies every other address and every name, which is tested; its pieces moved out of `conftest.py` (which had reached the line cap) into `tests/network_support.py`. The server tests run on asyncio only. `core/errors.py` is untouched at 295 lines: C4 added no error class, and the rule stays that the next one splits that module first.
- Evidence: the published surface (identity, instructions, descriptions, annotations, input schemas against their models and against hand-written literals, output schemas) through the in-process client; each tool over the four recorded companies arriving as the service returned it; Xiao-I's hand-worked values through the wire; every error class on every tool through a stub service and the reachable ones through the recorded stack (an unknown company, a 503, a malformed body, the directory down on both sides of the tier table's ninth row); the forged rule set; the canary; the concurrency test; the startup cases in process and in subprocesses; the guards, each with a self-test. 48 scripted mutations (each tool made synchronous or dispatched to a thread, the lifespan opening twice or never closing, a fifth tool, a renamed tool, each annotation, each of the five texts, a signature default drifting from its model, the text copy indented or out of step with the structured content, the structured content in JSON mode, each error row's readability, the contact in a message, a swallowed error, the exit code, the startup message, the preflight, the log level and handler, a dotenv file read, and each boundary guard) were each caught, with the files restored byte for byte.
- Options considered: one model-typed parameter per tool (rejected: `{"args": ...}` with a `$ref`, and it does not forbid stray keys either); the SDK's default text copy (rejected: indented, a third larger for no reader's benefit); a prose summary as the text (rejected: the spec expects the serialized JSON and a text-only host would see no data); text only with no output schema (rejected: no published contract); `str(exc)` as the error message (rejected: SEC-derived text would reach the model); a service seam chosen by an environment variable or a module hook (rejected: reachable from outside); letting a bad cache directory fail inside the lifespan (rejected: a traceback and exit 1 instead of a readable exit 2); reading a `.env` file (rejected: the working directory is the host's choice).
- Why: the adapter should add nothing the service does not say, publish exactly the contract the models enforce, keep an internal fault from looking like the caller's mistake, never let anything but the protocol touch stdout, and fail at startup in words a person configuring a host can act on.
- Revisit if: the SDK gains a way to forbid extra argument keys or to take a model as the whole input; a remote transport, a second concurrent client, or a host stall appears (move the service onto a dedicated owning thread); a host is observed forwarding both payloads to the model (trim the views or drop the structured copy); or the live smoke shows a host that rejects the nested `$defs` in `check_standards`' schema.

### D46: The tool service: four tools as plain methods, the tier table, and what an argument may be
- Date: 2026-10-31
- Decision: `tools/` gains the service that fills D45's models: `ToolService` with `resolve_company`, `list_filings`, `extract_financials` and `check_standards`, built by `open_tool_service(settings)`. No tool takes a price, a market input or a date. Today is the UTC date of the injected clock, the rules applied are the ones in force on that date, and every assessed `TierResult.as_of` equals the result's `evaluated_on` (pinned by test), so the date a reader sees is the date the rules were chosen for. The market conditions (price, market value, holders, market makers) are never supplied, so they stay not measured instead of being answered from a caller's word, and no argument schema contains a field that could carry one (a test walks every schema).
- Arguments: the four argument models are strict, frozen and closed to extra fields. The company is three optional fields, exactly one of which must be given (`cik`, `ticker`, `name`), never one free string classified by its shape, because a name such as NVIDIA is also ticker-shaped. Structural problems (types, lengths, the `limit` range, the shape of `forms`, an unknown enum value) are Pydantic constraints and raise `ValidationError` before the service runs. The one domain-level refusal is `ToolArgumentError` (none or several selectors, a CIK that is not digits, a ticker or name the domain types refuse), raised in `company_ref_of` only. Argument code never raises the base `InputValidationError`: Pydantic lets an exception that is not a `ValueError` propagate unchanged out of a validator, and the server will mask the bare base class as an internal failure, which is what it is when an engine model refuses a broken invariant. A table of 33 refusals asserts each is a `ValidationError` or a `ToolArgumentError` and never the bare class, an AST test pins that `args.py` raises nothing else, and a forged rule set (a standard with no requirements) shows an engine refusal inside `check_standards` leaves as exactly the base class. `list_filings` matches form types whole and without regard to case, so `10-k` matches `10-K` and not `10-K/A` (no prefixes, no wildcards), returns newest first, defaults to 20 and is capped at 100, and its `returned`, `total_matching` and `omitted` always add up.
- The tier table: `check_standards` always tries the directory and keeps a failure instead of raising it, then `select_tiers` (pure, no I/O) applies ten rows. A match is an exact `Symbol` equal to one of the SEC's tickers, a test issue never matches (it is counted in `test_issues_ignored`), and the category selects the tier (Q Global Select, G Global, S Capital). Row 1, initial with no tier named: all three tiers, `how=all_tiers_initial`. Row 2, initial with a tier named: that tier, `named`. Row 3, continued with a tier named: that tier, `named`, the directory result shown beside it so a mismatch is visible. Row 4, continued with none named and no ticker: none, `no_tickers`. Row 5, tickers but no non-test match: none, `no_match`. Row 6, matches in one recognized tier: that tier, `directory`. Row 7, matches in several recognized tiers: each distinct tier in Tier order, labeled by the tickers that selected it, `directory_mixed`. Row 8, a matched row whose category is blank or not recognized: none, `directory_unrecognized_category` (never a subset assessed silently, and an unrecognized status never blocks, it is reported raw). Row 9, continued with none named, at least one SEC ticker and the directory unreadable: the typed ingestion error is raised, because a tier cannot be guessed. Row 10, rows 1 to 4 with the directory unreadable: the assessment proceeds and the directory's state is reported. `how` states only how the tier was selected and never the directory's state, which lives in `directory.available` and `directory.error`; `CheckStandardsResult` echoes `requested_tier` beside `listing_type` and `pathway`. Each row has its own test, including a test issue never matching, mixed categories, an unrecognized category, no tickers, and the directory failing on both sides of row 9.
- No XBRL facts: a company the SEC has no companyfacts for gives `facts_status=no_xbrl_facts`, an empty snapshot (no figures, no gaps) and the engine on that empty bag, so every figure-based rule is not measured with `gap_reason` absent; nothing is invented. It is a result, not an error.
- The profile and the wiring: `CompanyProfile` (tickers, exchanges, entity type, as the SEC spells them) is read through `EdgarRepository.company_profile` and `IngestionService.company_profile` from the same cached submissions the resolution read, so resolve and profile cost one request. `open_cached_client` is extracted from the ingestion wiring so that every repository of the service shares one transport, one throttle bucket, one cache connection and one close; `open_tool_service` hands the directory repository the client's `forget`, so a download that arrives as a 200 but does not parse is evicted instead of served for an hour (proven by an end to end test that fails the first call and succeeds the second). `ToolSettings` never reads a `.env` file (a host can launch the server from any directory), takes the SEC contact from `SEC_EDGAR_CONTACT` through the inherited check, and requires `LISTINGLENS_CACHE_DIR` as an absolute path with no default. The contact goes to the SEC hosts and never to nasdaqtrader.com (a test captures the outgoing headers of a whole `check_standards` call).
- Sizes (serialized as the SDK will send them, UTF-8 bytes, maximum over Trans American, Luckin, GE and Xiao-I): resolve_company 427, list_filings at the default of 20 6,113, at the cap of 100 28,454, extract_financials 6,339, check_standards for one continued tier 22,501, for an initial listing with all three tiers 76,892 (Luckin). Ceilings are pinned at 2 KB, 8 KB, 32 KB, 8 KB, 25 KB and 80 KB. The three-tier ceiling is 80 KB rather than the 75 KB first planned, because the measured result is 1,892 bytes over 75 KB. A ceiling is a regression guard, not a budget, so it was raised rather than trimming the view now; trimming waits until the Phase 4 agent measures what these results cost in tokens.
- Housekeeping: `core/errors.py` is at 295 lines, so the next error added splits that module first.

### D44: One set of shapes for the Nasdaq directory's fields, and a malformed download is evicted from the cache
- Date: 2026-10-31
- Decision: this corrects D43's committed code. D43 left the directory's field rules in several places that could disagree: the category and status pattern (`[A-Z]?`) was written three times (the citation, the row model, the parser), and the parser accepted a Security Name of only whitespace (including a non-breaking, em or ideographic space) that `DirectoryLocator` refused, so `NasdaqDirectory.locator()` could raise on a row the parser had accepted. `NasdaqDirectory.url` and `.sha256` were free strings while the locator required a Nasdaq Trader URL and 64 lowercase hex digits. - Date: 2026-10-31
- Decision: Phase 3 is an MCP server that is a thin adapter over an in-process `ToolService` (D1), on local stdio (D2), with no FastAPI (D17). If the directory cannot be read, a continued-listing call with no tier named and at least one ticker needs it and fails with the typed message; every other combination proceeds, reports that the directory was unavailable with the error's message, and returns no Nasdaq status. A failure is always visible, and supplementary evidence failing never discards an assessment that did not depend on it. Initial listing is encoded for `traditional_ipo` only, so any other pathway honestly returns "no rule in force", never a pass.

Stdout is the protocol wire: nothing prints, logs go to stderr, and a real-stdio subprocess test proves `tools/list` round-trips without touching the network. ### D40: The margin rollup and tier verdict: three-valued logic, a thin flag, and a verdict that never rests on what was not measured
- Date: 2026-10-21
- Decision: `margin/rollup.py` rolls commit 1's per-rule results (D39) up the ruleset's own structure to a tier verdict. `rollup_set(standard_set, inputs, policy)` walks a `StandardSet` from `Ruleset.set_for`, calls `measure_rule` once per rule, and re-derives no per-rule state; `assess(ruleset, ...)` is the selection followed by the rollup and takes a loaded `Ruleset`, so the module still loads, fetches, and extracts nothing (the D39 import guard covers the new files).
- Logic: Kleene's three values. `clear` and `at_risk` are TRUE, `breached` is FALSE, `not_evaluable` is UNKNOWN. A branch is an AND of its rules, a requirement an OR of its branches, a standard an AND of its requirements, and a tier is the AND of every tier-common requirement and an OR across the standards. The two primitives (`and_all`, `or_any`) are written once. OR is FALSE only when every input is FALSE, so `or_any(FALSE, UNKNOWN)` is UNKNOWN. UNKNOWN is never turned into FALSE: FALSE can only come from a FALSE leaf, which is a measured breach. That is proved, not argued: `tests/test_margin_kleene.py` enumerates every assignment of {true, false, unknown} to the leaves of four structures shaped like the real ones (up to 3^8) and checks the engine against an independent possible-worlds brute force (complete each unknown both ways with plain booleans; true if every completion is true, false if every completion is false), and asserts that no assignment of only true and unknown leaves ever yields FALSE and that every FALSE value has a FALSE leaf.
- Two degenerate shapes are handled explicitly: a set with no standards (Rule 5315, tier Global Select initial, which has 6 common requirements and none) is just the AND of its common requirements, because an OR over nothing would be FALSE and make the tier unmeetable; and an empty set (no rule in force for that tier, listing type, and pathway) is `cannot_determine` with `rules_in_force` false and value UNKNOWN, because an AND over nothing is TRUE and would read as a pass. 18 of the 30 selections are non-empty; the other 12 (initial listing for the four other pathways) are the empty case.
- at_risk is a flag, not a fourth value: `thin` marks a node that is TRUE but rests on at-risk evidence, and it is false on every node that is not TRUE. An AND is thin when it holds and any part is thin; an OR is thin when it holds and every part that is true is thin, so a requirement met comfortably one way is not called thin because another way is at risk. A standard can hold thinly.
- The verdict: `does_not_meet` only when the tier value is FALSE; `at_risk` when TRUE and thin; `meets` when TRUE and not thin; `cannot_determine` when UNKNOWN (the common case: financials clear, but market makers, price, holders, or a multi-year series are unmeasured). `meets` cannot occur on the real ruleset yet: nearly every standard has a derived market-value condition, and D39 makes the engine raise `MarginConfigError` when all of a derived rule's drivers are on hand (no formula), which the rollup lets propagate. `meets`, `at_risk`, and `does_not_meet` are tested on hand-built sets and on real structures with external inputs supplied for holders, market makers, and shares.
- Result models: `BranchResult`, `RequirementResult`, `StandardResult`, and `TierResult` are frozen and strict, carry their truth and thin flag beside their children, and carry the per-rule results beneath them. Each validator re-derives value and thin from its children with the same primitives, and the tier also re-derives its verdict and its translated figures and requires the caveat to be non-empty exactly when the verdict is `cannot_determine`, so a forged result is rejected (D34, D35, D39).
- The financial signal is kept apart from the completeness gap. It is the same rollup run a second time with every rule that needs a non-EDGAR input assumed met ("if market makers, float, holders and price are all fine, how do the EDGAR-measurable conditions look?"), read as `clear`, `at_risk`, `breached`, or `undetermined`. A standard that tests nothing in EDGAR (a pure market-value standard) is `undetermined`, not vacuously clear. At the standard level a `breached` signal always means the standard's real value is FALSE (assuming more conditions met can only raise a value), and a validator enforces it. The tier-level signal summarizes the standards that test something in EDGAR (a vacuous standard would otherwise count as met and hide the rest), so it can read `breached` while the verdict is `cannot_determine`: every financial standard fails and only a market-value-only path remains open. It is not tied to the tier value. This was found by running the real sets: the first version read "clear" on an empty snapshot.
- The caveat says exactly what confirming a tier would need, counting only the conditions that still decide it: a subtree that is already TRUE or FALSE contributes nothing, and a standard counts only if the any-standard part is itself unknown. It has `missing_inputs` (deduplicated, in `InputKind` declaration order), `absent_concepts` (EDGAR figures not extracted), `needs_multi_year` (a window waits on a series), and `needs_year_end_balance` (only a quarter-end balance is on hand). The fourth part goes beyond the three planned: without it a rule blocked only by a quarter-end balance would leave an UNKNOWN tier with an empty caveat. It is empty unless the verdict is `cannot_determine`.
- Translations: every measured result under the tier contributes its figure's `TranslationNote`s, deduplicated by the figure's citation into `TranslatedFigure(figure_citation, translations)`, so a verdict resting on a convenience-translated USD figure (Luckin) still carries the rate and the home-currency pointer (D34, D39).
- Soundness note: Kleene treats each unknown leaf as independent. Two unknowns that share one missing input (the market price) can leave the tier UNKNOWN where that one input would decide it. That errs toward `cannot_determine`, never toward a false `does_not_meet`.
- Tests and mutations: hand-worked oracles independent of the engine. `tests/test_margin_kleene.py` (truth tables cell by cell, the thin rules, and the possible-worlds oracle), `test_margin_verdicts.py`, `test_margin_rollup_models.py` (forgeries), `test_margin_rollup.py` and `test_margin_findings.py` with `tests/margin_scenarios.py` (20 hand-worked verdict scenarios over synthetic structures; caveat pruning, ordering, and deduplication; translations; the financial signal), and `test_margin_tier.py` (the real ruleset structure: all 18 non-empty sets against an empty snapshot, a snapshot of only gaps, and a nine-figure snapshot are `cannot_determine` and never `does_not_meet`; a tier-common breach, a short holder count, every 5450 standard breached through the shares count, and the no-standards tier are `does_not_meet`; a derived rule with all drivers on hand stops the rollup). 53 scripted mutations (including `or_any` returning FALSE or TRUE on `(FALSE, UNKNOWN)`, an UNKNOWN tier mapped to `does_not_meet` or `meets`, not-evaluable treated as false or true, the empty-set guard, the no-standards shape, each thin rule, every validator, the caveat pruning at each level, the financial assumption, and the translation dedupe) were each caught, with the files restored byte for byte. Three survived at first (a forged tier value that agrees with a forged verdict, an unknown rule inside an already-failed branch, and a two-year window) and tests now pin each.
- Options considered: a literal "any at-risk condition anywhere makes it thin" (rejected for OR nodes: it would flag a requirement met comfortably); a fourth truth value for at risk (rejected: it is a flag on a true condition); treating no standards as FALSE (rejected: Rule 5315 would be unmeetable); catching the derived-rule error in the rollup (rejected: it hides a missing formula); a tier-level financial signal over every standard (rejected: a standard with no financial test would read as vacuously clear); a caveat over every unknown condition (rejected: it would name inputs that cannot change the answer).
- Why: the verdict is only useful if "does not meet" is a claim about the company and never about our coverage, so a missing figure, an unmeasurable condition, and an open alternative all stay UNKNOWN until a real measurement says otherwise, and the caveat names what would settle it.
- Revisit if: a price source and a derived-quantity formula are added (then `meets` becomes reachable and the rollup stays unchanged), a series is added (the multi-year branches become measurable), a standard needs a different thin rule, or the financial view should treat a non-EDGAR condition as other than met.

### D39: The margin-check engine, per-rule layer: four states, a cushion, and not-evaluable that names what is missing
- Date: 2026-10-21
- Decision: `margin/` is a pure function of a `FinancialSnapshot` (through an `Inputs` bag) and a ruleset's policy: `measure_rule(rule, inputs, policy)` returns one result per rule. No network, no extraction, no ruleset loading, no prose. This is the per-rule layer only; the rollup and the tier verdict are the next commit and the real-data tests the one after. Four states: `clear` (the figure clears the threshold by more than the cushion), `at_risk` (it meets the threshold but sits within the cushion), `breached` (it fails the threshold), and `not_evaluable` (it cannot be measured). **A missing figure is never a breach.** The two are different shapes: a measured result (clear, at risk, breached) carries the figure's citation, the rule's citation, the measured value, the threshold, the signed headroom, and the headroom ratio; a not-evaluable result carries the rule's citation and the reasons, and has no number, no headroom, and no figure citation, so it cannot be read as a breach. A model validator re-derives a measured result's state from its own numbers, so a forged state is rejected, as in D34 and D35.
- Order of work is the safety property: every reason a rule cannot be measured is collected first, and only a rule with none reaches the threshold comparison. A test sweeps all 105 real rules against an empty snapshot and against a snapshot of nothing but gaps and requires every result to be not evaluable; another changes every figure to a huge negative number and requires the set of unmeasurable rules not to change.
- Not-evaluable reasons are resolved generically by checking what a rule needs against what is on hand, not hard-coded per metric. Three kinds, kept distinct: `concept_absent` (the concept is not in the snapshot; chunk 12's `GapReason` is carried when a `ConceptGap` exists), `input_required` (the rule's `requires` names external inputs that are not on hand, and the specific `InputKind`s are named in `missing_inputs`, in `InputKind` declaration order), and `window_mismatch` (what is on hand does not fit the window). A rule can fail for more than one reason, and all are kept in the fixed order concept_absent, input_required, window_mismatch, with the first as `primary` (a cash-flow rule over three years is both `input_required` and `window_mismatch`).
- Window matching: a window needs 1 annual period (instant, latest fiscal year), m (`n_of_last_m_fiscal_years`), or `years` (`aggregate_over_fiscal_years`). A snapshot holds the latest period, so a multi-year window is a `window_mismatch` that says how many periods it needs and how many are on hand. An instant window takes a balance with any label and refuses a flow. A latest-fiscal-year window takes a full-year flow (extraction keeps only those, D31) and takes a balance only if it is the fiscal-year-end one, which is decided by the citation's fiscal-period label being `FY`; a `Q1` to `Q3` label, or no label (GE's 8-K facts), is a mismatch. The recorded fixtures label every 10-K and 20-F fact `FY` and every 10-Q fact `Q1` to `Q3`, so the test separates a year-end balance from a quarter-end one; commit 3 checks it against them. Unknown is not-evaluable, never a pass and never a breach. The concept's instant-or-flow kind is read from `extraction.aliases` rather than restated.
- Band math (exact, never rounded across an edge): headroom is `measured - threshold` for gte and gt and `threshold - measured` for lte and lt, so positive means the passing side; gt and lt fail at equality, gte and lte pass. breached if it fails; at_risk if it passes with headroom at most `cushion * |threshold|` (the edge itself is at risk); clear if it passes by strictly more. Classification multiplies and compares in a 100-digit context and never divides; the headroom ratio (`headroom / |threshold|`, `None` for a zero threshold) is reported only. The absolute threshold uses `copy_abs`, because `abs()` rounds to 28 digits. A zero threshold has a zero band: gte at 0 is at risk, anything above is clear. Pinned by a hand-written table of 37 cases and by 31-digit cases.
- The cushion: `RulesetPolicy.cushion = CushionSetting(default_ratio, basis)`, shipped as `0.10` in `policy.yaml` with its basis, an exact `Decimal` with `0 <= ratio < 1`. It is one ratio for every rule; the name leaves room for per-metric overrides, which are not built. The engine reads it from the policy it is given and never fixes it. The two synthetic policy fixtures under `tests/` gained the same block.
- The inputs seam: `Inputs` holds the snapshot's figures and gaps, an `external` mapping of `InputKind` to `Decimal` (empty today), and the annual periods on hand per concept (1 per figure). Resolution asks it four questions (`figure`, `gap`, `value_of`, `annual_periods`), so a later price adapter or series fills it without changing the resolution. There is no series field and no price source here, because nothing evaluates a series yet: a multi-year window with enough periods on hand raises a typed `MarginConfigError` rather than measuring only the latest figure. An external input that is on hand is measured directly as the value (with no figure citation, and the input named instead). A snapshot that lists a concept twice, or as both a figure and a gap, is refused.
- Loud refusals (`MarginConfigError`, a new typed error): a derived quantity whose drivers are all on hand (no formula is registered, and no market-value definition is invented); a rule or policy requiring the reported currency (`TranslationPolicy.REQUIRE_REPORTED_CURRENCY`); and a rule with a proxy under a policy that turns proxies on. None is used by the shipped ruleset. Silently measuring in USD, or ignoring a proxy, would answer a different question than the rule asks.
- Convenience translation (D34): a translated figure is still measured in USD, unconverted, and the result carries one `TranslationNote` per twin (its unit, which points at the `ReportedTwin` on the figure, the reported value, and the implied rate). `rule_verified` is carried on every result so an unverified rule, including a stayed one, is resolved and marked (D32).
- Guard: `tests/test_repo_constraints.py` forbids `margin/` from importing `httpx`, `listinglens.ingestion`, or the executable extraction modules (`service`, `figures`, `selection`, `corroboration`), the way `extraction/` is guarded; the static `extraction.aliases` table is the one allowed import. A self-test pins the finder on each.
- Tests and mutations: hand-written oracles independent of the engine, in `tests/test_margin_band.py`, `_windows.py`, `_models.py`, `_resolve.py`, `_ruleset.py`, `_inputs.py`, and `_periods.py`, with `tests/margin_factory.py` to build figures and snapshots. With a full fiscal-year snapshot exactly 22 of the 105 real rules are measured and 83 are not (12 multi-year concept rules, 25 derived, 46 external). 67 scripted mutations (including a missing figure measured as zero, a missing figure falling through to the comparison, an absence reason dropped, a missing external input measured as zero, every comparison and boundary, the exact context, `abs`, each window count and the `FY` test, the cushion read, the refusals, the validators, the inputs checks, the policy validator, the shipped value, and the guard) were each caught, with the files restored byte for byte. Two mutations survived at first (the period count reported for an external or derived rule); a test now pins that wording.
- Options considered: a single reason per not-evaluable result (rejected: a cash-flow rule fails two ways and both are worth naming); inferring the fiscal-year-end balance from the filing form (deferred: the label is already on the citation); a series field now (rejected: untestable until something evaluates a series); letting a derived rule with every driver on hand stay `input_required` (rejected: it would be untrue); a ratio test for the band (rejected: dividing can round across an edge).
- Why: the margin is only worth reporting if "we could not measure it" and "it fails" are never confused, so the engine is built around making a missing figure unable to reach a comparison, and around saying exactly what is missing so the next step knows what to supply.
- Revisit if: a price source or a series is added (extend the bag and the measurement, not the resolution), a rule needs a per-metric cushion, the fiscal-year-end label proves unreliable for a filer type (use the form), or the reported-currency or proxy policies are turned on.

### D35: Income from continuing operations falls back to net income only when pre-tax minus tax corroborates it
- Date: 2026-10-13
- Decision: when an issuer tags neither `IncomeLossFromContinuingOperations` element (D33), net income stands in for `INCOME_FROM_CONTINUING_OPERATIONS` at an accession and full-year period (same accession, start, and end, USD) only if three facts at that key reconcile exactly: pre-tax income (the `PRETAX_INCOME` candidates in alias order, the first with a fact at the key), `IncomeTaxExpenseBenefit`, and net income, with pre-tax minus tax equal to net income. The subtraction runs in a 100-digit decimal context (`exact_difference`), because the default 28 digits would round 10**30 + 1 down to 10**30 and report an identity that does not hold. A missing fact, a fact at another accession, period, or unit, or two different values for one tag at one key means the key is not a candidate; nothing is guessed. The target stays the parent measure, consistent with parent-first D33.
- Which net income: `NetIncomeLoss` (the parent measure) needs no witness. `ProfitLoss` is the total including the noncontrolling interest, so it counts only with a witness: a nonzero `NetIncomeLossAttributableToNoncontrollingInterest` fact at the key vetoes it; a present and zero NCI income fact passes it (`nci_income_is_zero`); with no NCI fact, `NetIncomeLossAvailableToCommonStockholdersBasic` equal to `ProfitLoss` passes it (`common_equals_total`, since NCI income and preferred deductions are then both nil); anything else refuses, because absent NCI facts prove nothing. The common-stockholder figure is a witness only and is never a value. If both identities hold, `NetIncomeLoss` wins. Discontinued operations break the identity the same way and leave a gap (no fixture has them, so that case is synthetic).

The citation records the tag actually used.

### D34: A translated figure carries the reported-currency twin and the implied rate; D31's flag enriched
- Date: 2026-10-13
- Decision: when a USD figure is a convenience translation (D31), `FinancialValue` now carries the figure the filer actually reported, not just a bool. `reported_twins: tuple[ReportedTwin, ...] = ()`, where `ReportedTwin` (frozen, strict, `extra="forbid"`) holds `unit` (for example `CNY`), `value` (exactly as reported, nothing converted), `period` (identical to the figure's), and `implied_rate` (the reported value divided by the USD value, that is units of the reported currency per one USD; `None` when the USD value is zero). A reader, and chunk 14, can therefore show the home-currency figure beside the translated USD one and say at what rate. `is_convenience_translation` stays a stored field. A computed property would be tidier, but `computed_field` over `@property` needs a `type: ignore` under this mypy plugin, which the project bans, so a validator keeps the flag equal to `bool(reported_twins)` in both directions, exactly as `unit` and `period` already track the citation. The tuple is the right type for a cross-border tool even though no fixture has a second twin unit.
- Validation (`FinancialValue` keeps its unit and period checks): the flag equals `bool(reported_twins)`; twin units are unique; no twin is in the figure's own unit; each twin's period equals the figure's; and `implied_rate` equals the recomputed `translation_rate(twin.value, figure.value)`, so a forged or stale rate is rejected. `ReportedTwin` itself refuses a rate that is not positive. The formula lives in one function, `translation_rate`, used both to build a twin and to check one. A pair that cannot be a translation of each other (opposite signs, or a zero reported value against a nonzero USD value) fails these checks as `InputValidationError`, which `build_figure` already reports as `MalformedPayload` at `...units.USD.reported_twins`, so no raw error escapes.
- Selection: `_has_twin` (a bool) became `_reported_twins`, returning one `(unit, fact)` per other unit that holds a fact with the same accession, start, and end, sorted by unit, taking the latest-filed fact if a unit repeats the period. Money only, as before: a share count never has a twin. `Selection` keeps `is_convenience_translation` as a property over the tuple, so the existing callers and tests are unchanged and all 1033 of them passed before any new test was written.

### D32: Listing standards as a versioned ruleset: typed schema, strict YAML loader, rulesets packaged in the library
- Date: 2026-10-12
- Decision: `standards/` holds the schema and loader for the Nasdaq listing standards (D7, D10, P2-H). This commit encodes no Nasdaq content: every threshold, quotation, and condition is Gate 1 content for the next commit (D33), and the tests run on synthetic records marked "not Nasdaq content" (`tests/fixtures/standards/synthetic/`, ids `SYN-`, urls `example.invalid`; a test enforces the marker). Layout: `enums.py`, `quantities.py` (inputs, derived quantities, units), `metrics.py` (metrics and windows), `rules.py` (the rule record, citation, verification, policy), `ruleset.py` (grouping and as-of selection), `checks.py` (cross-record checks), `loader.py`, `yaml_loader.py` (the only module that imports PyYAML; a test pins that). `load_ruleset(source)` reads every `*.yaml` rule file and the required `policy.yaml` from a directory-like source and returns a `Ruleset`.
- Location, a refinement of D7: the ruleset YAML lives inside the package, `src/listinglens/standards/rulesets/nasdaq/`, and is found with `importlib.resources`, not in a root `standards/` directory. Reason: root-level data is not packaged in the Hatch wheel, so a deployed server could not load its own rules. Verified rather than assumed: `uv build --wheel` contains `listinglens/standards/rulesets/nasdaq/policy.yaml`, and with the wheel itself on `PYTHONPATH` (so the package imports from inside the zip) `default_source().iterdir()` lists it and `load_ruleset()` loads it. `test_a_ruleset_loads_from_inside_a_zip_archive_as_it_does_from_a_wheel` keeps the zip path covered in the suite; the loader takes any directory-like `Traversable`, so tests pass a `tmp_path`.
- The record, one requirement per record (D7): `rule_id` (stable across versions), `exchange`, `tier` (`global_select`, `global`, `capital`), `listing_type` (`initial`, `continued`), `pathways` (non-empty; every rule is `traditional_ipo` for now), `standard_id` and `standard_name` (set together, or both omitted for a tier-common rule), `requirement` and `branch`, `metric`, `window`, `comparison` (`gte`, `gt`, `lte`, `lt`), `threshold` (exact `Decimal`), `threshold_unit` (`usd`, `usd_per_share`, `shares`, `count`), `effective_from` (inclusive), `effective_to` (exclusive, or open), `citation` (rule section, https rule url, verbatim quotation, retrieval date, optional SEC release and url, which come as a pair), `verification` (a verified rule records who and when, and not before the citation was retrieved), optional `proxy` and `translation_policy`. Initial rules are scoped to the IPO circumstance by `pathways` (Gate 0 S2); there is no separate listing-circumstance field, and the other circumstances are Phase 7.
- Grouping (Gate 0 S8): a Standard is the rules sharing a `standard_id`, and all of its requirements must hold. A StandardSet is every tier-common requirement plus at least one standard. Gate 0 S4 found compound shapes a flat record cannot hold, so alternatives exist below the standard level too: rules sharing a `requirement` are alternatives by `branch` (a requirement holds if any one branch holds, and a branch holds if all of its rules hold). That expresses "the most recent fiscal year, or two of the last three" (two branches of one requirement) and "one value, or a pair with equity" (a one-rule branch against a two-rule branch). A rule with no `requirement` is its own requirement. Selection is `Ruleset.set_for(exchange, tier, listing_type, pathway, as_of)`; an empty result is `is_empty`, never a pass.
- Metrics and inputs (Gate 0 S6): a tagged union of `concept` (a chunk 12 `TargetConcept`), `derived` (a registered `DerivedQuantity` with declared inputs), and `external` (an `InputKind`: `market_price`, `publicly_held_shares`, `holder_count`, `market_maker_count`, `operating_history`). `StandardRule.requires` is computed from the metric, never set on the record, so there is one source of truth: a rule that needs `market_price` is not evaluable from EDGAR alone, and chunk 14 reports it as such instead of failing it. Two derived quantities are registered because Gate 0 names them, with only their non-EDGAR drivers declared; Gate 1 completes each definition from the cited text. The threshold unit must equal the metric's unit, checked by the model. Open flag for Gate 1: `operating_history` is a count of fiscal years, so it uses unit `count`, because Gate 0 S7 gave no years unit; confirm against the rule text.
- Windows (Gate 0 S5): `instant`, `latest_fiscal_year`, `n_of_last_m_fiscal_years` (needs 1 <= n <= m), and `aggregate_over_fiscal_years` (years >= 2, sum). Every multi-year form tests the rule's own comparison and threshold, so there is no separate per-year-floor field: "positive in all three years" is `n=3, m=3`, `gt`, `0`; "a minimum in each of the two most recent" is `n=2, m=2`; the three-year aggregate is its own rule. The two multi-year forms (`n_of_last_m_fiscal_years` and `aggregate_over_fiscal_years`) are exactly what chunk 12 cannot feed (it extracts only the latest period), so those rules are `not_evaluable` until a series extension exists; the schema carries them either way. A check that a flow concept uses a fiscal-year window is left to commit 2's consistency test, which can read `extraction.aliases` without making `standards/` depend on `extraction/`.
- History (Gate 0 S9, S10): thresholds are moving by date, so every record carries `effective_from` and `effective_to`, versions of one `rule_id` must not overlap and must keep their tier, listing type, and standard, and `effective_from` is inclusive while `effective_to` is exclusive so versions tile without a gap. Chunk 13 ships current rules only; history is backfilled into the same schema when the eval needs it. Effective status of recent amendments is confirmed at Gate 1.
- The strict loader neutralizes the YAML 1.1 behaviors that would change a value silently, each pinned by a test and a mutation: duplicate keys are rejected (PyYAML keeps the last), non-string keys are rejected, anchors, aliases, and explicit tags are rejected before any value is built, `yes`, `no`, `on`, `off`, and capitalized `True` stay strings (only `true` and `false` are booleans), integers are plain decimals only (`0755`, `0x1F`, `1_000`, `1:30`, and `1e3` stay strings), a decimal token becomes an exact `Decimal` from its source text (an 18 digit threshold keeps every digit, D27), dates stay strings so the shared ISO gate decides them (D28), the file is capped at 1 MiB, and only one document is allowed. A key with no value is the empty string, not null, on purpose: a half-edited `effective_to:` must not silently become an open-ended rule, and every field rejects an empty string; `~` or `null` is the explicit way to say none. A merge key `<<` is only an ordinary key that the schema then refuses. Every failure is a `StandardsConfigError(path, record, field, detail)` with a bounded detail that never echoes input; no `ValidationError`, `YAMLError`, `OSError`, or `KeyError` crosses the boundary. PyYAML 6.0.3 and `types-pyyaml` are pinned exactly; `uv audit` found no vulnerabilities in the 28 locked packages.
- Config models are not model-level strict, unlike the extraction models (D26): YAML supplies strings for enum members, which strict mode rejects. Each int, bool, number, and date field carries its own strict gate instead (a float, string, or bool threshold is refused; `verified` must be a real boolean; a datetime or a numeric string is not a date). A typed caller may pass a `date` object.
- Two shared pieces moved to `core/` so `standards/` does not import `ingestion/`. By the architect's ruling on shared helpers, `core/validation.py` now holds the bounded error summary that `parse_or_raise` used (count, first three locations, 2,000 characters, input never echoed), and `MalformedPayload` and `StandardsConfigError` both use it; the 788 existing tests passed untouched, which is the proof of no drift. Not covered by a ruling and recorded for review: the ISO date gate moved from `ingestion/payloads/dates.py` to `core/dates.py` (`git mv`, three import lines and the test file renamed to `test_core_dates.py`); D28 is left as written and still names the old path. It was the one piece of the standards schema that would otherwise have imported from `ingestion`, or been copied, and D28 rejected a copy per module.
- Policy (rulings 6, 7, 10), recorded in `rulesets/nasdaq/policy.yaml` with a stated basis: `translation: allow_flagged` (a convenience-translated USD figure may feed a USD threshold unconverted and the result carries the flag; a cited rule on Q9 may override it per rule) and `proxy: off` (a rule's explicit proxy is used only when this is on, and the result says "via proxy"). These are our decisions, not Nasdaq claims, so they carry no verification. A rule with `verified: false` may be evaluated by chunk 14 and is marked unverified in the result; the Phase 5 eval and release gate refuse to certify on unverified rules.
- Dropped as unprovable by mutation, per the project rule: `utf-8-sig` decoding (PyYAML already skips a leading byte order mark; the BOM test stays as a pin), an explicit non-finite threshold check (pydantic's `Decimal` already refuses NaN and infinity, as D27 found; a test pins it), and a "no empty standard" check (a standard is derived from its rules, so it cannot be empty).
- Evidence: 58 scripted mutations (each YAML guard, the record gates, every cross-record check, the metrics and windows, selection and grouping, the loader's file rules, and the shared summary) were run with every file restored byte for byte. Of the four first uncaught, two guards were the dead code above, one mutation was ineffective (it widened a regex but not the resolver's first-character list) and was redone, and one needed a test that the file order does not depend on the source's listing order, which a reversed-listing source now proves. Every remaining mutation is caught.
- Options considered: `tomllib` (rejected by the architect: the signed decision is YAML, and the strict loader neutralizes its footguns); a root `standards/` directory (rejected: not packaged in the wheel); a `listing_circumstance` field now (rejected: only the IPO circumstance exists until Phase 7, and `pathways` scopes it); a separate per-year-floor field on the window (rejected: it would duplicate the rule's own threshold); model-level strict config models (rejected: strict rejects the strings YAML supplies); copying the date gate into `standards/` (rejected: D28).
- Why: the ruleset is the thing the margin engine grades against, so its shape must make a wrong rule unrepresentable (a unit that does not match its metric, an unverified rule that claims a date, overlapping versions, a number that went through a float), its source must be auditable to a quotation and a release, and it must load the same from a source tree and an installed wheel.
- Revisit if: Gate 1 shows a condition the record cannot express (for example a conditional threshold), the rule text gives `operating_history` a unit other than a count of years, a standard is renamed between versions (the name check is per standard, across all versions), or the packaged data grows enough to need a different resource layout.

Literal first-present-wins would return a stale year for an issuer that abandoned a tag (for example `Revenues` for `RevenueFromContractWithCustomerExcludingAssessedTax`); the synthetic stale-tag test pins that, and on all three recorded fixtures both rules choose the same tag. They are three distinct errors under `ExtractionError` and three distinct `ConceptGap` reasons, because a just-public company with no annual figure is a different situation from an issuer that does not tag the concept, and chunks 13 and 14 read the gaps programmatically. ### D28: Payload dates are gated on ISO shape, not string type; D27's date claim corrected
- Date: 2026-10-10
- Decision: `ingestion/payloads/dates.py` defines the one gate every payload date and datetime field uses: `IsoDate`, `IsoDateTime`, and `OptIsoDate`, built from three `BeforeValidator` functions. A value is accepted only if it is a `str` that fully matches the ISO shape (`fullmatch`, never `$`, so a trailing newline cannot pass); pydantic then validates the calendar values (`"2023-13-45"` and `"2023-02-30"` are still rejected by it). A date accepts only `YYYY-MM-DD`. A datetime requires `YYYY-MM-DDTHH:MM:SS`, an optional fraction, and an explicit zone (`Z` or an offset); a naive datetime or a date-only string is rejected. `OptIsoDate` maps `None` and the empty string to `None` and otherwise applies the date gate, written out explicitly rather than depending on the ordering of `EmptyStrAsNone` validators. Chosen shape-based and shared because the defect is in the gate logic, so a copy per module would copy the bug.
- Correction of D27: D27 said `filed`, `end`, and `start` "accept ISO strings only". That was wrong as built. The chunk 11 gate checked only `isinstance(value, str)`, and pydantic's lax parser reads a numeric string as a Unix timestamp, so `"0"` became 1970-01-01, `"1696032000"` became 2023-09-30, and, for a datetime, `"20230930"` became 1970-08-23T03:42:10Z. The chunk 11 tests only tried integers and `"20230930"` (rejected for a `date` only because 20,230,930 seconds is not a midnight timestamp), which gave false comfort. D27 is left as written and corrected here; the corrected gate is the one above.

- Evidence the existing data is unchanged: the recorded fixtures carry exactly three date shapes, `YYYY-MM-DD`, `YYYY-MM-DDTHH:MM:SS.mmmZ`, and `""` for `reportDate` (172 of 414 values). Before any change, a digest of every date and datetime value parsed from all eight date-bearing recorded fixtures (the five submissions files and the three companyfacts files; count, first, last, and a SHA-256 over the isoformat values, 36 entries, stored in `tests/fixtures/date_digests.json`) was taken from the old models; `test_every_recorded_fixture_date_parses_to_the_same_value_as_before_the_gate` asserts the same digests afterwards, which proves every existing value parses to the same value, not merely that it still parses.
- Verified behavior: list-element failures report the aliased, indexed path (`filingDate.1`, `filings.recent.filingDate.1`, `reportDate.1`, `acceptanceDateTime.1`, `formerNames.0.from`, `formerNames.0.to`, `filings.files.0.filingFrom`, `filings.files.0.filingTo`) with the url threaded. ### D27: Typed companyfacts payload models; val as Decimal; parse_or_raise hardened; recorder extended
- Date: 2026-10-10

### D26: Citation locators and the companyfacts URL builder; D5's field lists superseded
- Date: 2026-10-10
- Decision: `domain/citation.py` defines the citation types as pure vocabulary: no parsing, no fetching. `Citation = Annotated[XbrlLocator | TextLocator, Field(discriminator="kind")]`, with a defaulted `kind: Literal["xbrl"]` or `Literal["text"]` tag on each arm, so callers never pass `kind`, a bad payload yields one `union_tag_invalid` error, and the pattern is clean under `mypy --strict` with the pydantic plugin. `XbrlLocator` fields: `cik: Cik`, `taxonomy: Taxonomy` (`us-gaap`, `dei`), `concept`, `unit`, `period: XbrlPeriod`, `accession_no: AccessionNumber`, `form_type`, `fiscal_year: int | None`, `fiscal_period: str | None`, `source: XbrlSource` (`companyfacts`, `frames`). `TextLocator` fields: `cik`, `accession_no`, `document_name`, `section_label`, `anchor_text`, `char_start`, `char_end` (`char_start >= 0` and `char_end > char_start`). `XbrlPeriod` is a discriminated union of two models, `InstantPeriod(instant)` and `DurationPeriod(start, end)`, so an instant with a start or a duration without one cannot be represented; a duration with `end < start` is rejected, and `end == start` is allowed. `concept` must fully match `[A-Za-z][A-Za-z0-9_]{0,254}` and `unit` must fully match a letter-led token with an optional `/token` (`USD`, `shares`, `pure`, `USD/shares`), using `fullmatch` so a trailing newline cannot pass; there is no enumerated unit set. ### D24: FullTextSearchRepository pages EFTS by arithmetic, signals truncation, and guards pre-2001 coverage
- Date: 2026-10-06
- Decision: `ingestion/search_repository.py`'s `FullTextSearchRepository(client: EdgarClient, *, page_size=100, result_window=10000)` exposes `search(query, *, forms, start_date, end_date) -> FullTextSearchResult`. The 2001-01-01 constant lives in the repository, not in `endpoints.full_text_search_url`, which stays a pure builder with no policy. - Paging and the cap: offsets start at 0 and advance by `page_size`. - Coupling: `full_text_search_url` emits no `size`, and the recorded fixtures were made against EFTS's server default of 100, so `page_size` must equal that default for offsets to tile contiguously. Both `page_size` and `result_window` are injectable (default 100 and 10000) so tests can exercise the cap with tiny windows; changing `page_size` in production without adding a `size` parameter to the builder would skip or repeat hits.
- Accepted over-signal: `truncated` is inferred from a full page at the last in-window offset, not from the total. A result set that has exactly `result_window` hits therefore reports `truncated=True` although nothing was lost. This errs toward the safe direction (a caller is told the result may be incomplete) and costs one spurious flag at an exact boundary.
- Unexpected statuses: any non-2xx the transport did not retry raises `UpstreamError(attempts=1, detail="unexpected status, not retried")`, the same shape as D23; a non-JSON body raises `MalformedPayload`.
- Options considered: Putting the 2001 guard in `full_text_search_url` (rejected: the URL builder is pure and shared, and coverage is a repository policy); adding a `size` parameter to the builder (rejected for this chunk: the fixtures were recorded against the no-size default, so the cap constant stays in the repository); detecting the cap by requesting past it and catching `MalformedPayload` (rejected: it spends a request to learn what arithmetic already knows, and string-sniffing `detail` is fragile); deriving `truncated` from `total` (rejected: `total` is a `gte` floor of 10000 once results exceed the window, so it cannot say whether the window was reached).
- Why: Verified live during the Phase 1 investigation (D15) that pre-2001 queries return HTTP 200 with zero hits, a silent wrong answer, so they need a typed refusal rather than an empty result; verified live in chunk 6 (D22) that the window boundary is exact at `from + size <= 10000`. - Revisit if: A caller needs more than the first 10,000 hits per query (narrow by date range, or build the continuation), or a `size` parameter is added to the URL builder, at which point `page_size` should be passed through to it.

### D21: SQLite HTTP cache wraps EdgarTransport; wall-clock TTLs, fail-open on both read and write
- Date: 2026-09-22
- Decision: `ingestion/cache.py`'s `CachedEdgarClient` wraps an already-constructed `EdgarTransport`, exposing the same `get(url) -> httpx.Response` shape; `EdgarTransport` gets no new parameter and stays unaware caching exists. `classify_ttl(url)` is a pure function over `urlsplit(url).hostname.lower()` and `.path` (lowercased to match `assert_allowed`'s canonical form), returning `IMMUTABLE` for anything under `www.sec.gov/Archives/edgar/data/`, `CONDITIONAL` for the ticker map, and `SHORT` (a safe default) for everything else, including endpoints not built yet. The `Clock` protocol (`ingestion/throttle.py`) gained a `time() -> float` method, implemented as `time.time()` in `RealClock`; the cache uses only `.time()`, never `.monotonic()`, for `fetched_at` and freshness comparisons. Both `_read` and `_write` fail open: a `sqlite3.Error` or a corrupt stored row is treated as a cache miss and never propagates, and a failed write (disk full, locked, permissions) is swallowed so the already-fetched response is still returned. Only `2xx` responses are persisted. Response headers are serialized via `dict(headers.items())`, which keeps only the last value of any repeated header name; an accepted, deliberate limitation, since EDGAR GET responses have not been observed to repeat a header name.
- Options considered: Store `fetched_at` via the throttle's existing `Clock.monotonic()` (rejected: verified `time.monotonic()`'s reference point is undefined across process runs, and the cache DB persists across runs by design, so a monotonic comparison would silently corrupt every TTL check after the first restart); inject the cache into `EdgarTransport` itself versus wrap it in a separate client (wrap chosen, keeps the transport onion-pure); build real `If-Modified-Since`/304 handling for the ticker map now versus defer it (defer chosen: nothing fetches the ticker map yet, that lands with chunk 7's name/ticker resolution, so building it now would have no caller); raise from a failed cache write versus swallow it (swallow chosen, extending the same fail-open principle already applied to reads, since a write happening only after a successful fetch means an uncaught write error would turn a successful request into a failed one, which the cache exists to never do).
- Why: The cache is explicitly disposable, best-effort local infrastructure (per D4's original framing); it must never be able to turn a working request into a failure, in either direction (read or write). `classify_ttl`'s safe default and host/path-only matching keep it forward-compatible with endpoints not yet built (companyfacts) without needing to be touched again, and keep it honest against the ingestion-layer constraint test (no form-name literals, no `domain.pathway` import).
- Revisit if: Chunk 7 actually needs the ticker map, at which point real conditional revalidation (an optional `extra_headers` parameter on `EdgarTransport.get`, a 304-aware branch in `CachedEdgarClient.get`) replaces the `CONDITIONAL` class's current plain-TTL stopgap. Note: chunk 5 does not provide a shared static type across `EdgarTransport`/`CachedEdgarClient` (no Protocol or Union); if a caller ever needs to hold either interchangeably under strict mypy, that is chunk 7's job to add when it actually needs it, not something this chunk delivers.

### D20: Ingestion failure errors carry url and enough last-observed evidence to diagnose the cause
- Date: 2026-09-17
- Decision: Three new leaves under `IngestionError` in `core/errors.py`: `ResponseTooLarge(host, url, limit_bytes)`, `TooManyRedirects(host, url, max_redirects)`, `UpstreamError(host, url, status_code: int | None, attempts, detail: str | None)`. `UpstreamError.status_code` is `None` for a transport-level failure (connect timeout, connection refused, no HTTP status exists) with `detail=str(exc)`; it carries the last HTTP status with `detail=None` on 5xx exhaustion. `RateLimited` is enriched in place rather than replaced: it now also carries `url`, `attempts`, the last `content_type`, `undeclared_tool_fingerprint` (whether the response body matched the "Undeclared Automated Tool" signature), and `retry_after_seen` (whether the header was present at all, independent of whether it parsed), alongside the existing `retry_after_seconds`. Its message states plainly that this response shape can also indicate a rejected User-Agent rather than true rate limiting. No fourth `RetriesExhausted` leaf: the transport retries every retryable condition itself, so `RateLimited` and `UpstreamError` are only ever raised at exhaustion in this layer, and enriching those two in place is the complete diagnosable-exhaustion surface.
- Options considered: A single generic `RetriesExhausted(host, status_code)` leaf for every exhaustion case (rejected: collapses a genuine 5xx, a transport-level failure with no status, and a rate-limit-or-rejected-UA ambiguity into one shape, losing exactly the evidence needed to tell them apart); enrich the two leaves that already exist for these cases, plus one clearly-scoped new leaf per genuinely new failure mode (chosen).
- Why: A persistent failure must be diagnosable from the exception alone, without re-running the request. The guiding principle going forward: every ingestion failure error carries `url` like the others already do, plus enough last-observed evidence (status code or its absence, content type, a matched body fingerprint, whether an expected header was present) to diagnose the real cause, and it never asserts a cause the response does not actually prove, which is exactly why the HTML-shaped 403 is raised as `RateLimited` with evidence attached rather than as a confident `MissingUserAgent` the transport cannot actually verify at that point.
- Revisit if: A future failure mode needs evidence that doesn't fit any existing leaf's fields; extend that leaf rather than adding a new one unless the cause is genuinely distinct.

The environment supplies only a contact address, via `SEC_EDGAR_CONTACT` (`core/config.py`'s `Settings.sec_edgar_contact`), not the full User-Agent. Chunk 4's transport calls `branding.user_agent(settings.sec_edgar_contact)` to build the real header.
- Options considered: Keep the full composed User-Agent string in the environment (`SEC_EDGAR_USER_AGENT`), with `core/config.py` validating it against a full placeholder (the shape built in the branding refactor's first draft); supply contact only and compose the header from branding (chosen).
- Why: Carrying the full UA string in the env var would make `branding.user_agent()` dead code with no real caller, source the product name in every outgoing request from user-typed `.env` text rather than from the one authoritative constant, and reintroduce a product/version string in `.env.example` that can silently drift from `core/branding.py`. Supplying contact only means the operator can never mistype or go stale on the product identity half of the header; only `core/branding.py` can change it.
- Revisit if: A future deployment needs the operator to override the full User-Agent string outright (unlikely under SEC's fair-access policy, which asks for identifying contact info, not a specific product string).

### D18: pydantic mypy plugin adopted; typed models expose a strict constructor plus a parse() classmethod for untrusted input
- Date: 2026-09-10
- Decision: The pydantic mypy plugin is enabled project-wide (plugins = ["pydantic.mypy"]) with init_typed = true and init_forbid_extra = true. Typed value models (the identifiers) therefore expose two entry points: the plain field constructor for already-clean typed values, and a parse(raw: object) -> Self classmethod that validates arbitrary external input and raises a typed InputValidationError. Untrusted or external input goes through parse(); internal typed code uses the constructor.
- Options considered: Widen field types (for example Cik.value: int | str) or scatter per-call type ignores to keep one flexible constructor (rejected: reintroduces the coercion and the untyped surface the plugin exists to remove); adopt the plugin and split the API (chosen).
- Why: disallow_any_explicit flags every BaseModel subclass because pydantic's own BaseModel.__init__ is typed with an explicit Any; the plugin's synthesized per-model __init__ removes that. init_typed then makes the constructor reject loose input at type-check time, which is the reject-not-coerce rule enforced statically. The parse() split gives untrusted input one explicit validating doorway. Chunks 6 and 7 must follow this convention for any new typed model that ingests external data.
- Revisit if: A model needs a genuinely open or polymorphic input shape that the two-entry-point pattern cannot express cleanly.

### D17: No FastAPI dependency in Phase 1
- Date: 2026-09-06
- Decision: Phase 1 adds no FastAPI application or HTTP framework, even though FastAPI is listed in the project stack.
- Options considered: Scaffold a FastAPI app now so it exists when needed later; add it only when a transport actually needs it.
- Why: The approved MCP transport is local stdio (D2), and nothing before a remote deployment needs an HTTP app. Adding FastAPI now would be dead code with no caller.
- Revisit if: Remote MCP transport (see D2) is scheduled and needs an HTTP entry point.

### D16: Citation model deferred to Phase 2
- Date: 2026-09-06
- Decision: `domain/citation.py` and the `Citation` discriminated union (D5) are not implemented in Phase 1, despite being listed in the Phase 0 MCP tool contracts.
- Options considered: Define the citation shape now from the brief's description; wait until the first real extraction service exists.
- Why: Nothing in Phase 1 emits a citation. `Pathway` is defined now (D14 note below) because the enum is fixed and reused unchanged everywhere; `Citation`'s exact shape should instead be driven by the first real `XbrlLocator`/`TextLocator` use in Phase 2's extraction layer, not guessed in advance.
- Revisit if: Phase 2 extraction work begins.

### D15: Known-failing baseline is a session hook over real unhandled edge cases, not a test-observed comparison
- Date: 2026-09-06
- Decision: The CLAUDE.md-required "recorded known-failing baseline" for Phase 1 is `xfail_strict = true` plus a small git-tracked `tests/known_failing.txt`, compared in a `pytest_sessionfinish` hook gated to full-suite runs. It lists exactly three genuinely unimplemented items: legacy non-UTF-8 document decoding, name-to-CIK resolution for issuers absent from `company_tickers.json`, and EFTS `search_after` deep pagination beyond the roughly 9,900-result cap.
- Options considered: A pytest test that compares the baseline file to the live xfail set (rejected: a test cannot observe the outcomes of tests that have not yet run, so this is not implementable as a test); a broader baseline that also xfails `filings.files` pagination overflow, pre-2001 full-text-search coverage, and ambiguous ticker resolution (rejected: verified live that overflow must be implemented in Phase 1 since it is the common case for the target long-history dataset, that pre-2001 EFTS queries return HTTP 200 with zero hits, a silent wrong answer that needs a typed `OutsideFullTextCoverage` guard rather than an xfail, and that ambiguous ticker resolution should be a passing test asserting a typed ambiguous result); an empty baseline (rejected: proves nothing until populated, and the three items above are real known gaps worth recording now).
- Why: `xfail_strict` already delivers the requirement that matters, an XPASS fails the run, so drift toward silently regressing is caught. The baseline file's only added value is documenting genuinely unbuilt capability, so it should contain only that.
- Revisit if: The baseline grows past about five items, at which point the mechanism itself should be reconsidered.

### D14: Form-agnostic ingestion
- Date: 2026-09-06
- Decision: The ingestion layer accepts filing form types (`forms: frozenset[str]`) as a caller parameter and hardcodes no IPO form set. Foreign-issuer forms (the F-series: `F-1`, `F-1/A`, `F-1MEF`, plus `DRS`, `DRSLTR`, `CORRESP`, `UPLOAD`, `20-F`, `6-K`) are supported from Phase 1, not deferred to Phase 7 as the Phase 0 brief's literal "S-1 or 424B" scoping implied.
- Options considered: Hardcode an `IPO_FORMS` constant (`S-1`, `424B`) inside the ingestion layer per the brief's literal wording; accept forms as a caller-supplied parameter with no hardcoded set (chosen).
- Why: Three reasons, in order of weight.
  1. Ingestion stays interpretation-free. Deciding that `F-1` and `424B4` constitute "the IPO path" while `424B2` usually does not (it is typically a shelf takedown, not an IPO prospectus) is a classification judgment. It belongs in the analysis layer's `PathwayClassifier`, not in a transport client. A hardcoded form set would be exactly the kind of interpretation leak the onion architecture (see project-level architecture notes) is meant to prevent.
  2. The foreign-private-issuer population needs the F-series now, not in Phase 7. Verified live against Luckin Coffee (CIK 1767582), the canonical China fraud and delisting case and the deepest part of the project's stated moat: its complete filing history contains zero `S-1` filings. It filed `F-1`, `F-1/A`, `F-1MEF`, `DRS`, `DRS/A`, `DRSLTR`, `EFFECT`, `UPLOAD`, `CORRESP`, `20-F`, `6-K`, `CERT`, and `25-NSE`. An `S-1`-only ingestion client returns nothing for the exact population this project exists to analyze.
  3. Phase 7 never has to touch this layer. De-SPAC (`S-4`, `F-4`, `DEFM14A`), reverse merger (Super `8-K`), and the bilingual foreign-issuer work (O5) all become caller-supplied form sets against an unchanged ingestion client. The high-signal artifacts already visible in Luckin's own history, `UPLOAD` (SEC comment letters) and `CORRESP` (issuer responses), stay reachable from Phase 1 rather than being designed out by a narrow form allowlist.
- Revisit if: A future phase needs ingestion itself to filter or rank by form type rather than simply fetching what the caller asks for; that would be a sign the boundary needs to move.

## Phase 0 decisions

Recorded here as a permanent log; approved in the Phase 0 architecture sign-off prior to this session. Rationale is summarized from the approved brief, not re-litigated.

### D13: Peer selection is deterministic, versioned config
- Date: 2026-09-06
- Decision: `compare_to_peers` selects peers by pathway, size band, recency, and sector, as versioned config rather than an ad hoc model judgment.
- Options considered: Let the agent or a model call select comparable peers at run time; select peers via deterministic, versioned selection criteria (chosen).
- Why: Peer comparison needs to be reproducible and explainable like the standards checks and the red-flag weights, not a one-off LLM judgment that could vary run to run.
- Revisit if: The eval shows the deterministic criteria produce poor peer sets for a pathway or sector.

### D12: Demo UI deferred to Phase 6, video plus run-it-yourself preferred over hosting
- Date: 2026-09-06
- Decision: The optional Next.js/React demo UI is deferred to Phase 6. A recorded two-minute video plus a run-it-yourself-with-your-own-key path is preferred over a live public host; if hosted later, it sits behind rate limiting and a hard per-day cost cap.
- Options considered: Build the demo UI early alongside the core agent; defer it and lead with a recorded video and self-hosting instructions (chosen).
- Why: Avoids taking on hosting cost and abuse surface before the core agent and eval harness, which are the actual moat, are proven.
- Revisit if: A live demo becomes necessary for a specific audience (for example, an interview) before Phase 6.

### D11: Deterministic eval metrics maximized; LLM-as-judge scoped to memo prose only
- Date: 2026-09-06
- Decision: Eval metrics are maximized as deterministic (precision/recall/F1 against real outcomes, extraction numeric fidelity, citation faithfulness, injection resistance). LLM-as-judge is used only for memo prose quality, at temperature 0 against a fixed rubric on a cheap model, with a human-audited sample and cached judgments.
- Options considered: Use an LLM judge broadly across metrics; restrict LLM-as-judge to the one genuinely subjective metric and keep everything else deterministic (chosen).
- Why: Deterministic metrics are cheap, reproducible, and safe to gate a release on. LLM-as-judge is reserved for prose quality, the one dimension that is not otherwise measurable, and constrained to stay reproducible and cheap.
- Revisit if: A deterministic proxy for prose quality is found, or judge cost/variance becomes a problem even at the constrained scope.

### D10: First pathway and ruleset is traditional_ipo on Nasdaq
- Date: 2026-09-06
- Decision: The first implemented pathway and listing-standard ruleset is `traditional_ipo` against Nasdaq initial and continued listing standards. NYSE and foreign-issuer standards land in Phase 7.
- Options considered: Build multiple pathways or exchanges in parallel from the start; sequence a single well-documented pathway and exchange first (chosen).
- Why: Bounds Phases 1 through 6 to the best-documented pathway and exchange before tackling multi-route pathway detection and foreign-issuer complexity in Phase 7.
- Revisit if: Early eval cases turn out to concentrate on NYSE or a non-IPO pathway, making this sequencing a poor fit.

### D9: Typed CompanyRef resolved to CIK and echoed everywhere
- Date: 2026-09-06
- Decision: `CompanyRef` (cik, ticker, or name) is resolved to a CIK and echoed back in every tool output.
- Options considered: Let each tool re-resolve or silently assume the company; resolve once to CIK and echo it in every output (chosen).
- Why: CIK is the one stable EDGAR identifier; tickers and names are ambiguous and change over time, so every output must state unambiguously which company it resolved to.
- Revisit if: Multi-entity outputs (for example, a SPAC and its de-SPAC target) need more than one CIK echoed at once.

### D8: Deterministic weighted red-flag scoring in v1
- Date: 2026-09-06
- Decision: `RedFlagScorer` uses deterministic weighted scoring in v1, with versioned weights in `risk/weights.yaml`. A learned component is added only if the eval harness justifies it.
- Options considered: Train a learned scoring model from the start; start with deterministic weighted rules and only add learning if evaluated performance demands it (chosen).
- Why: Matches the minimal-over-engineering constraint and keeps the model auditable and explainable before a labeled set large enough to justify learned weights exists.
- Revisit if: The Phase 5 eval shows deterministic weights plateau below an acceptable precision/recall bar.

### D7: Standards are versioned YAML, one rule per record
- Date: 2026-09-06
- Decision: Listing standards live in `standards/<exchange>/*.yaml`, one rule per record, each with a primary-source citation and an `effective_from` date. All numeric thresholds are flagged to-verify rather than asserted.
- Options considered: Hardcode thresholds in code; store them as versioned, git-diffable YAML with citations (chosen).
- Why: Listing standards change over time and must be auditable to their primary source; YAML keeps them reviewable and out of code, consistent with the "structured, schema-validated, never free-text" constraint.
- Revisit if: A rule needs conditional logic that outgrows a flat YAML record.

### D6: Qualitative extraction locates sections deterministically, then structures with a bounded LLM call
- Date: 2026-09-06
- Decision: `QualitativeExtractionService` first locates sections (risk factors, related-party, ownership/VIE) deterministically, then performs schema-constrained LLM structuring inside a bounded, sanitized envelope.
- Options considered: Let the LLM find and structure sections in one open-ended pass; separate deterministic location from constrained structuring (chosen).
- Why: Matches the security stance that filing text is untrusted data, never instructions. Deterministic section location keeps the LLM's job narrow, bounded, and auditable rather than open-ended.
- Revisit if: Deterministic section location proves too brittle across filing formats and needs a fallback.

### D5: Citation is a discriminated union of XbrlLocator and TextLocator
- Date: 2026-09-06
- Decision: `Citation` is a discriminated union: `XbrlLocator {concept, context_ref, unit, period, accession_no, source_url}` for financial values, `TextLocator {accession_no, form_type, filed_date, section_label, verbatim_anchor, char_span?, source_url}` for qualitative claims.
- Options considered: One generic citation shape for both financial and qualitative claims; a discriminated union with a distinct shape per source kind (chosen).
- Why: Financial values and qualitative claims resolve to structurally different locations (an XBRL concept/context versus a text span), and citation faithfulness is a graded eval metric targeting 100%, so each kind needs to be independently and precisely resolvable.
- Revisit if: A third citation kind (for example, a tabular non-XBRL figure) is needed.

### D4: HTTP-layer cache, disposable, separate from the eval store
- Date: 2026-09-06
- Decision: Caching happens at the HTTP layer, keyed by URL, in a disposable cache DB that is a separate SQLite file from the eval store.
- Options considered: Cache at a higher layer (for example, per extracted value); cache raw HTTP responses only, kept structurally separate from eval data (chosen).
- Why: Keeps the cache purely a performance and SEC-politeness layer that can be deleted and rebuilt at any time, and keeps it structurally isolated so eval results are never contaminated by cache eviction or rebuild.
- Revisit if: A higher-layer cache (for example, extracted `FinancialFacts`) becomes necessary for cost reasons.

### D3: Golden-set labels are git-tracked fixtures; results and baseline are gitignored SQLite
- Date: 2026-09-06
- Decision: Golden-set case labels are git-tracked JSON fixtures (`eval/cases/*.json`) loaded into SQLite at run time. Eval results (`eval_result`) and the recorded baseline (`eval_baseline`) live in gitignored SQLite, keyed by `git_sha`.
- Options considered: Track everything (labels, results, baseline) in git; track only the curated labels in git and keep run-generated data out of history (chosen).
- Why: Labels are curated, reviewable data that should be diffable in git. Run results and the baseline are regenerated by running the harness and would bloat history if tracked, while still needing to be keyed to a specific `git_sha` for the release-gate comparison.
- Revisit if: Reproducing a specific historical eval run without re-running it becomes a real need.

### D2: Local stdio transport by default, remote HTTP later behind auth
- Date: 2026-09-06
- Decision: The MCP server uses local stdio transport by default. Remote HTTP transport is later work, and only behind authentication.
- Options considered: Build remote HTTP transport from the start; start local-only and add remote later behind auth (chosen).
- Why: Avoids exposing a network-facing service before authentication exists. Consistent with D12's deferred-hosting stance for the demo.
- Revisit if: A remote MCP consumer (for example, a hosted demo backend) is scheduled.

### D1: MCP tools are thin wrappers over an in-process ToolService
- Date: 2026-09-06
- Decision: MCP tools are thin wrappers over a single in-process `ToolService` facade. The agent dogfoods the server over a stdio MCP client. The eval harness calls `ToolService` directly, in-process.
- Options considered: Put tool logic directly in the MCP server handlers; centralize all logic in one `ToolService` facade and make the MCP layer a thin schema-validating adapter over it (chosen).
- Why: Keeps one source of truth for logic. The MCP layer stays a thin, typed, schema-validating adapter, and the eval harness can exercise the same logic the agent uses without needing a live MCP round trip for every eval run.
- Revisit if: `ToolService` methods start needing MCP-specific behavior that does not belong in the eval or agent paths.
